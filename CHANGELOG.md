# Changelog

## 2.2.0 (2026-10-22)

- Compiled stylesheet for projects without Tailwind: `dist/acun-ui.css` (npm export `@acunsoft/acun-ui/acun-ui.css`, also on jsDelivr/unpkg), built from the same Tailwind v4 source with `npm run build:css`: Tailwind's preflight, the tokens and both built-in themes, the form base and every class the free components use, minified (17 KB gzip). The components, the light and dark theme, `data-theme` sections, the primary colour, focus and hover states paint as they do in a Tailwind application (checked in Chrome by `tests/js/css-parity.test.mjs`). `tailwindcss` is now an optional peer dependency. Acun Pro has `dist/acun-pro.css` (the free file plus the Pro components; the storefront is not in it). A plain HTML example: `examples/html/index.html` in the repository.
- The kit's global rules (the theme's line on a border without a colour class, the pointer cursor, the headings' letter spacing, the code font, the dark font smoothing and the page texture) moved from `css/panel.css` into `css/base.css`; the rest is `css/core.css`. `css/panel.css` imports both, so nothing changes for applications. Import `css/core.css` (or link `dist/acun-ui-core.css`) for no global rules from the kit.

- The kit draws its own form controls: the `@tailwindcss/forms` plugin is no longer needed. Every `<input>`, `<select>` and `<textarea>` a component renders (fields, select, textarea, checkbox, radio, switch, search, input group, segmented control, chip group, command palette, theme switcher) carries a `data-acun-control` attribute, and the new `css/forms.css` (imported by `css/panel.css`) gives those controls the base the plugin gave them: no browser appearance, the frame and inner spacing, a 16px font on phones (iOS Safari does not zoom in on focus), the select's arrow, the checkbox and radio boxes with their check, dash and dot, the date fields' inner parts and the focus ring that the components' classes build on. The rules are adapted from the plugin's base strategy (MIT, THIRD-PARTY-NOTICES.md) with the same values, specificity and cascade layer, so the components look exactly as they did; the colours the components' classes always replace are the theme's tokens. Bare `<input>`, `<select>` and `<textarea>` elements of the application are no longer styled by the kit's install; add `data-acun-control` to one to give it the same base.
- `php artisan acun:install` no longer adds `@plugin '@tailwindcss/forms';` to the CSS entry or `"@tailwindcss/forms"` to `package.json`, and `--check` no longer lists them. A line that is already there is left as it is. Applications may remove `@plugin '@tailwindcss/forms';` and the devDependency (then run `npm install` and `npm run build`); keeping them is harmless, and a field the application writes itself without a component keeps the plugin's look only while the plugin stays (or with `data-acun-control`).
- List pages: Acun Pro's `php artisan acun:table` generator is removed. The kit's list parts (`acun:table` and its parts, `acun:list-toolbar`, `acun:search`, `acun:sortable-th`, `acun:selection-bar`, `acun:per-page-select`, the pagination view) are unchanged and work with the data table of your choice; their comments no longer mention the generator. Guide: https://ui.acunsoft.com/list-page.html

- `acun:datatables` (Acun Pro's new DataTables component) is in the list of Acun Pro tags: without `acunsoft/acun-pro` it stops with the error that says where the component is.

- Acun DataTable theme bridge: the new `css/acun-datatable.css` (imported by `css/panel.css`, outside any cascade layer) sets the `--adt-*` custom properties of Acun DataTable (`acunsoft/datatable-laravel`'s Livewire table and `@acunsoft/datatable-dom`, a separate MIT package by Acunsoft) from the kit's tokens (`--ac-surface`, `--ac-body`, `--ac-line`, `--ac-primary`, `--ac-radius`, `--ac-font-sans`…) on the table's outermost element. With the package's own stylesheet imported, the table follows the theme, its dark member, a section's `data-theme` and the user's primary colour; the package's own dark switch (`data-theme="dark"`, `.dark`, the system setting under `data-theme="auto"`) no longer decides. Colours, corners, the font and the shadow only: the package's sizes stay. Nothing changes on pages without the package, and it works the same with or without `acunsoft/acun-pro`. Docs: https://ui.acunsoft.com/components/acun-datatable.html

## 2.1.1 (2026-10-22)

- `php artisan acun:install`: Laravel's skeleton sets its own font (`--font-sans` in an `@theme` block of `app.css`), which overrides Acun UI's (Public Sans, DM Mono). An interactive run now asks to remove it (yes by default) and shows the removed lines; the block goes too when nothing else is left in it. `--remove-font` removes it without asking. Without interaction the line is left with a warning, as before (a script never changes the design by itself).

## 2.1.0 (2026-10-18)

- `php artisan acun:install` wires the package into a Laravel application, so the install is two commands: `composer require acunsoft/acun-ui`, then `php artisan acun:install`. It adds `"@acunsoft/acun-ui": "file:vendor/acunsoft/acun-ui"` and `"@tailwindcss/forms"` to `package.json`, `@plugin '@tailwindcss/forms'`, `@import '@acunsoft/acun-ui'` and the views' `@source` to `resources/css/app.css`, and `import '@acunsoft/acun-ui'` to `resources/js/app.js` (the starter kit's `resources/css/acun-ui.css` and `resources/js/acun-ui.js` when they exist); with `acunsoft/acun-pro` installed, that package's lines too, and it lists the steps left. Only missing lines are added and no file is created, so a second run changes nothing; an `@theme` block that sets `--font-sans` is left alone with a warning. `--example` copies an example page (`resources/views/acun/example.blade.php`), `--npm` and `--no-npm` run or skip the package manager's install and build (npm, pnpm, yarn or bun, by the lock file; asked when interactive), `--no-interaction` asks nothing. `--check` changes nothing: it lists every item with a fix for the missing ones and exits with 1 when something is missing. The package now requires `illuminate/console`, `illuminate/process` and `laravel/prompts`, which every Laravel application has.
- The theme switcher's screen reader texts say mode, not theme: "Switch to dark mode" and "Switch to light mode" (Turkish "Koyu moda geç", "Açık moda geç"), were "Switch to the dark theme" and "Switch to the light theme". An application that translates the old keys in its own `lang/*.json` renames them.
- `php artisan acun:install --check` with built assets (`public/build/manifest.json`) and no `node_modules` folder, as in the starter kit and the demos of the Acun Pro zip or on a server without Node.js, shows `node_modules` as a note (`!`), not as missing: the pages use the built assets, and Node.js is only needed to change the design.
- With one Vite entry per section, where the main entry does not import Acun Pro and others do (the demos' `resources/css/panel.css` and `resources/js/panel.js` next to a free `app.css` and `app.js`), `php artisan acun:install` adds and checks Acun Pro's lines in those entries and leaves the main one with the free lines.

## 2.0.0 (2026-10-18)

Details, with who is affected and how to fix each change: https://ui.acunsoft.com/upgrade.html

### Breaking changes

- One free package: `acunsoft/acun-ui-core` (the CSS and JS) and `acunsoft/acun-ui-free` (the Blade and Livewire components) are now `acunsoft/acun-ui` on Composer and `@acunsoft/acun-ui` on npm. The PHP namespace (`Acun\Ui\`), the service provider, the `acun-ui` view namespace, the `<acun:*>` tags, the config file and the publish tags are unchanged. Apps change their `composer.json`, the npm dependency (`"@acunsoft/acun-ui": "file:vendor/acunsoft/acun-ui"`), and the `@acunsoft/acun-ui-core` imports and `vendor/acunsoft/acun-ui-free` paths in their CSS, JS and Vite config.
- The `pro` block of `config/acun-ui.php` moved to `config/acun-pro.php` (`panel.assets`) in the paid `acunsoft/acun-pro`, which still reads a 1.x block until 3.0. The layouts include `acun-pro::layout-extras` (was `acun-ui-pro::layout-extras`).
- The panel shell moved to the paid `acunsoft/acun-pro`: the layouts `acun:layout.sidebar`, `horizontal`, `auth`, `message` and `print`, `acun:menu` with `Acun\Ui\Menu\Menu` (now `Acun\Panel\Menu`; the old name is an alias there until 3.0), `acun:nav.*`, `acun:user-menu`, `acun:filter-button`, `acun:filter-context`, `acun:auth-panel` and `acun:message-panel`, with their CSS (the content area and docked filter panel, the sticky top bar, the side menu) and their translations. This package keeps `acun:layout.head` and `acun:layout.blank`. An application with only this package that uses them adds `acunsoft/acun-pro`; with both packages nothing changes. Without it a paid tag stops with "… is an Acun Pro component (acunsoft/acun-pro) …".
- The PRO dialogs' 1.x variables `--ac-surface-subtle`, `--ac-border`, `--ac-border-strong`, `--ac-text`, `--ac-text-muted`, `--ac-radius-md` and `--ac-radius-lg` are gone, and `--ac-surface`, `--ac-primary`, `--ac-secondary`, `--ac-danger` and `--ac-shadow-*` are now design tokens (`--ac-danger` and `--ac-secondary` are those tones' fills). An application that set them sets the tokens instead (`--ac-line`, `--ac-ink`, `--ac-muted`, `--ac-radius`…).
- The components paint with the design tokens (`bg-surface`, `text-muted`, `border-line`, `bg-primary text-on-primary`, `bg-danger-tint text-danger-tint-ink`…) instead of palette shades and `dark:` classes, so each one follows the theme by itself. The light theme looks the same; in the dark theme a few shades are made consistent (secondary text is zinc-400, body text zinc-300, status text on a tint the 300 shade, status icons, dots and progress bars the 400 shade, a checked checkbox, radio or switch the primary fill, the light button dark grey). Application CSS or tests that look for a kit class (`text-gray-500`, `bg-brand-50`, `dark:bg-zinc-900`, `ui-btn-primary`…) use the token class instead.
- `.ui-btn`, `.ui-btn-*`, `.ui-btn-shadow` and the per-variant variables (`--btn-success-bg`, `--btn-light-color`…) are gone: `acun:button` uses the tone tokens (`bg-success hover:bg-success-hover text-on-success`, `shadow-success/90`). A theme changes a tone with `--ac-tone-success` (and so on). The primary colour's `--btn-primary-bg`, `--btn-primary-hover` and `--btn-primary-color` are gone too: the user's colour is `--ac-user-*` (below).
- The fields' focus shadow is `focus:shadow-(--ac-focus-shadow)` (`--ac-focus-shadow-danger` on an invalid field), which a theme sets in its block; `--ui-focus-shadow` and `--ui-focus-shadow-error` are no longer read.
- The mode and the theme are `data-theme` on `<html>`: the light or dark member of the page's theme pair (`light` and `dark` for the built-in one), by the mode (light, dark or system, followed live). `class="dark"` is still written next to it for application code until 3.0, but it no longer selects the dark tokens: a dark section is `data-theme="dark"`. The semi-dark menu is `data-theme="dark"` on the aside (with its `dark` class, for application markup, until 3.0).
- The user's colour: `data-brand-color` is gone. A preset or a custom #rrggbb is measured once against the hardest text backgrounds of the enabled themes and written on `<html>` as `--ac-user-fill`, `--ac-user-fill-hover`, `--ac-user-on-fill`, `--ac-user-tone`, `--ac-user-tone-dark` (and `--ac-user-fill-dark`, `-fill-hover-dark`, `-on-fill-dark` for a colour with its own dark fill); every theme block and nested section reads them first. Overrides of `--color-brand-600`, `--brand-custom-600`, `--ui-focus-ring`, `--ui-backdrop` and `--ui-backdrop-blur` are no longer read: a theme sets `--ac-tone-primary` (`--ac-focus`, `--ac-backdrop`…) in `:root, [data-theme] { … }`.
- The presets are colours, `Acun\Ui\Support\Appearance::COLORS` (`Layout::BRAND_COLORS` is an alias until 3.0; its `dark` entry is now `['light' => '#3f404d', 'dark' => '#474747']`). A swatch shows the real fill (green #008933, red #d83838, yellow #9f6b13, blue #038197, not the bright 500 shades). The config island sends `colors` (key => colour) instead of `brandPresets`. Measured, the dark preset's tone in a dark theme is #696a74 (it was the hand-picked #71717b).
- Browser storage: one JSON object per scope, `localStorage['acun-ui:{scope}']` (`mode`, `brandColor`, `skin`, `contentWidth`, `sidebar`, `navbar`, `semiDark`). The scope is the head's `scope` prop, else `Appearance::use(…, scope:)`, else `panel` in the panel layouts, else `config('acun-ui.layout.scope')`, else `app`; the storefront uses `shop`. So two products on one origin never share a colour or a mode. The 1.x keys (`appearance`, `brandColor`, `skin`, `contentWidth`, `sidebarCollapsed`, `navbarMode`, `semiDark`) are not read: users' saved choices reset once.
- `config('acun-ui.layout.mode')` is the mode's default and `layout.theme` a theme's key; a 1.x `light`, `dark` or `system` in `layout.theme`, in a `theme` prop or in `Layout::page(['theme' => …])` is read as the mode until 3.0. `acun:layout.head`, `acun:layout.blank` (and the panel layouts) take `mode` and `scope`. The config island carries `scope`, `theme` (`{key, light, dark}`), `targets`, `colors` and `mode`, and `defaults.mode` (was `defaults.theme`); the preference POST sends `{ mode }` instead of `{ theme }`.
- `rounded-sm` … `rounded-3xl` read `--ac-radius` and `font-sans`, `font-mono`, `font-brand` read `--ac-font-*`: an application's `@theme { --radius-sm: … }` or `--font-sans` override sets the token instead. The shadow utilities keep their composed values (a colour modifier such as `shadow-black/40` needs them).
- JS: `$store.appearance.value` is the mode and `toggle()` reads `data-theme`; `brandShades(color, targets)` returns `{ fill, hover, onFill, tone, toneDark }`.
- `bg-dark`, `text-dark`, `border-dark` and `outline-dark` are the dark tone: #3f404d in the light theme, the neutral grey #2e2e2e in the dark theme (it was #3f404d in both). The kit's components already paint another colour there with `dark:`; application markup without a `dark:` class gets the grey.
- `dark:` follows the nearest `data-theme` instead of the `dark` class: an element is dark inside a theme whose name ends in `dark` (`<html data-theme="dark">`, the semi-dark menu, a `data-theme="dark"` section) unless a light theme sits between them (a `data-theme="light"` island in a dark page, two levels deep). Application markup with `dark:` classes looks the same on the kit's layouts, which write both; markup that adds `class="dark"` by itself to darken a part writes `data-theme="dark"` instead. `class="dark"` is still written on `<html>` (and on the semi-dark menu) until 3.0, but no kit rule reads it: CSS that keys on `.dark` (`.dark .x { … }`) keys on `[data-theme$='dark']`, or uses `@variant dark { … }`, which follows sections.
- The 1.x theming CSS left `css/panel.css`: the `.dark` shadow colours (`--shadow-edge`, `--shadow-near`, `--shadow-far` and their `-xs`, `-md`, `-lg`, `-xl` forms), the bordered skin's `body.bg-gray-50` hook (the bordered page colour is the `--ac-page` token: a layout of your own paints its body with `bg-page`), `--ui-control-border` (now `--ac-control`), `--ui-table-box-bg` and `--ui-table-box-shadow`, and the base rules that set the body text, the headings, `color-scheme` and font smoothing from the palette or `.dark` (the theme blocks set them on every themed element). The shadow utilities compose the theme's layer tokens instead (`--ac-shadow-sm-edge`, `--ac-shadow-sm-near`, `--ac-shadow-sm-far`, and so on for `xs`, `md`, `lg`, `xl`), which `--ac-shadow-*` composes too: a theme changes a shadow by its layers' colours, and a colour modifier (`shadow-black/40`) still works. A border without a colour class is the theme's line (`--ac-line`; in the dark theme #2e2e2e instead of the light grey). Livewire's error dialog dims with `--ac-backdrop`.
- `acun:checkbox` rounds its box with the `--ac-radius-check` token (0.25rem in the built-in themes, the same as before) instead of `rounded-sm`, so a theme with large corners keeps square-looking checkboxes (Acun Pro's Vivid sets 0.375rem).
- The body paints the theme's page texture: `background-image: var(--ac-page-pattern)` with `--ac-page-pattern-size` (`none` in the built-in themes; Acun Pro's Atelier sets its paper dots). The layouts paint the colour with `bg-page`.
- One theme switcher: `acun:theme-toggle`, `acun:brand-color-picker` and `acun:theme-customizer` are wrappers of the new `acun:theme-switcher` until 3.0 (`as="button"`, `as="inline"` with the colour alone, `as="drawer"` named `theme-customizer`); their props are kept (`presets`, `custom`, `label`; `sidebar`, `title`). Their markup changed: a choice is a native radio in a radio group its heading names (`role="radiogroup"` with `<input type="radio">`), not a button with `role="radio"` or `aria-pressed`, so Tab enters a group once and the arrow keys move the choice; the colour swatch is the radio's `<span>` (the tick is unchanged). The customizer's skin, content width, menu and top bar sections are Acun Pro's (the panel layouts are), so with this package alone it shows the mode and the colour; its mode heading reads "Color mode" (was "Theme"). Application tests or CSS that look for `button[role="radio"]`, `aria-pressed` or the 1.x headings in them use the radios and the new headings.
- `lang/tr.json` lost the panel settings' keys, now Acun Pro's (`Bordered`, `Boxed`, `Collapsed`, `Content width`, `Dark menu`, `Expanded`, `Fixed`, `Hidden`, `No shadow, 1px border`, `Scrolling`, `Shadowed cards`, `The menu stays dark in the light theme`, `Top bar`, `Wide`); an application with only this package that uses them adds them to its own `lang/tr.json`.

### New

- Design tokens. `css/themes.css` sets the `--ac-*` roles of the built-in light and dark themes: the neutrals (page, surface, field, sunken, hover, track, inverse, line, control, ink, body, dim, muted, faint) and eight tones (primary, secondary, success, info, warning, danger, dark, accent), each with a fill, hover, `on-` text, ink, line, tint, soft and tint-ink colour, plus focus, backdrop, radius, font and shadow tokens. `css/tokens.css` turns the colours into Tailwind utilities that read the token on the element (`bg-surface`, `text-muted`, `bg-primary text-on-primary`, `border-line/80`). The kit's CSS entry imports both. `brand-*` (application code, until 3.0) follows the element's theme and the user's colour.
- `Acun\Ui\Support\Appearance`: `define($key, $light, $dark, $targets)` registers a theme pair (the keys `light`, `dark`, `system` and `default` are reserved, a dark member's name ends in `dark`), `use($key, scope:)` chooses the theme and the storage scope of a request, `pair()`, `light()`, `dark()` (`data-theme="{{ Appearance::dark() }}"` for a dark section), `targets()`, `colors()`, `presets()`.
- `AcunUI.isDark(element)` (the nearest `data-theme` ends in `dark`) and `AcunUI.tokenColor(element, '--ac-line')` (a token's colour on an element as `rgb()`), for code that draws in the theme's colours. `$store.brand.forget()` forgets the saved colour.
- The boot script gives the semi-dark menu (`data-acun-semi-dark`) and the navbar (`data-acun-navbar`) the browser's saved choice as the parser adds them, before the first paint: no flash of the server's value. `wire:navigate` restores `data-theme`, the user's colour and the menus; a page of another scope starts from that scope's choices.
- Section theming: a part of the page takes another theme with `data-theme` (the semi-dark menu is `data-theme="dark"` on the aside, a light island in a dark page `data-theme="light"`); its components, the docked filter panel and the menus in it follow its tokens, the user's colour included, and application code's `dark:` classes follow it too. A Chrome test measures the menu, the focus ring, every button and its counter, the badges, a field's placeholder, a dropdown's text and the docked panel in both, with two custom colours: text 4.5:1, focus ring and lines 3:1.
- `scripts/codemod-tokens.mjs` rewrites palette and `dark:` classes in your own views with the rules the kit used (`node vendor/acunsoft/acun-ui/scripts/codemod-tokens.mjs resources/views`, `--dry` to preview); it lists what it leaves for a person.
- Sections: the parts that stay light or dark in every theme are sections with their own `data-theme` (the QR code and the colour picker's tick are light, the carousel's controls sit on the picture in a light section).
- `acun:avatar`, `acun:avatar-group`, `acun:kbd`, `acun:skeleton`, `acun:switch`, `acun:empty-state` and `acun:copy-button` are free (they were PRO), with their translations.
- `Acun\Ui\AcunUi::addComponentPath($path, published: false)` adds a component folder to the `acun` prefix. Published copies (`resources/views/vendor/acun-ui/components/ui`, and Acun Pro's `vendor/acun-pro` and 1.x `vendor/acun-ui-pro`) are searched before both packages, whatever order Composer lists the providers in, so a copy keeps replacing its component after the component moved between the packages.
- `scripts/codemod-tokens.mjs` keeps a light-only opacity on a line token: `border-gray-200/80 dark:border-zinc-800` becomes `border-line/80`.
- `acun:theme-switcher`, the one theme switcher: the mode (light, dark, system), the primary colour (the presets and a colour of the user's own, measured for contrast as before) and, where a package offers them, the themes and its own sections. `as`: `button` (the navbar icon, light ↔ dark; a status tells a screen reader the new mode), `drawer` (a panel from the right; `trigger="edge"` the gear on the right edge, `trigger="button"` an icon button in place, `:trigger="false"` a trigger of your own; `name`, `title`, `label`, `description`) or `inline`. `sections` chooses the sections and their order (an array or `"mode,color"`; default mode, color, theme), `modes`, `colors` (true, false or key => [#rrggbb, name]), `custom` and `themes` (null: what a package offers on the request, false, or items) shape the switcher's own, `headings` hides the headings for a picker under a label of its own. `reset` forgets the scope's saved choices (`localStorage['acun-ui:{scope}']`, the other scopes keep theirs) and applies the defaults; `reset-url` makes it a link that also returns a server-side choice to its default. A choice that reloads the page (a theme, a language) opens the drawer again at once on the next page (`sessionStorage['acun-ui:{scope}:open']`). Choices are kept per scope: the storefront never changes the panel's colour or mode, nor the other way round.
- `acun:theme-switcher.section`: a section of the switcher, a heading and a radio group (`options` value => label or `['label', 'description', 'icon']`, as a segmented bar or as cards; `value` and `change` are Alpine expressions, `$store.navbar.mode` and `$store.navbar.set`) or your own controls in its slot; the switcher's own sections use it, and so can an application's, in the switcher's slot.
- `Appearance::section($name, $view)` adds a section to the switcher (Acun Pro adds the panel's skin, width, sidebar and navbar, and the storefront's header, footer, language and links); `Appearance::sections()`. `Appearance::offerThemes(fn () => [...])` sets the themes the switcher offers on a request and `Appearance::switchable()` reads them (cleaned by `Appearance::themeItems()`: a key and a link, an unsafe link becomes `#`).
- `Acun\Ui\Support\Contrast`: `luminance()`, `ratio()` and `whiteReads()`, the runtime's WCAG maths in PHP (a test checks they agree); the swatches' tick uses it.
- `$store.appearance.scope`: the page's storage scope.

### Fixed

- Focus rings (WCAG 2.2 non-text contrast): every `acun:button` variant's keyboard focus ring stands out 3:1 on the page, a surface, a field and a sunken area, in the light and dark themes and in a section of the other one. A colour's ring is its ink (`focus-visible:outline-success-ink`…): the `-line` shades are decoration, and the success, warning and info rings gave 1.75-2.21:1 on white. The white, ghost and light buttons' ring is the focus token (`line-hover` gave 2.39-2.62:1), as the primary, outline, soft and link buttons' already was. `acun:checkbox` shows its focus ring again (its `focus:outline-none` set the outline style to none for the ring too), and `acun:radio` draws the checkbox's ring, a focus outline on keyboard focus, instead of @tailwindcss/forms' ring on a white offset (a white halo in the dark theme). A Chrome test measures the focus ring of every button variant and of the tabs, chips, segmented control, switch, checkbox, radio, fields, search button, accordion, collapse, sortable column, theme toggle and colour swatches in every theme and section.
- The user's colour is measured against the light page too: `Appearance::TARGETS` (and the runtime's default) is `['light' => '#fafafa', 'dark' => '#1f1f1f']`, the light theme's page instead of its white surface, so link, outline and focus text in the user's colour reads 4.5:1 on the bare page (a light yellow, #ffd400, gave 4.32:1). The green, red, yellow and cyan presets' text tone in the light theme is a step darker (#008632, #d63737, #9c6913, #037e94; they read 4.35-4.43:1 on the page); their buttons, hovers and button text, and every dark-theme colour, are unchanged: the dark theme's tone starts from the colour's white-text shade, so the light target never changes it. A theme of your own gives `Appearance::define()` its darkest light text background, usually its page.
- The colour picker's own colour input shows a focus ring (the transparent input drew none) and the swatches are one tab stop with arrow keys (each was a tab stop of its own).

## 1.1.0

Details, with who is affected and how to fix each change: https://ui.acunsoft.com/upgrade.html

### New

- `input-class` on form fields styles the control itself; a class in it replaces the kit's class of the same kind, never the error frame.
- Modal and drawer parts can be drawn by a nested Livewire component.
- Dark-theme placeholders, the command palette's hints and button counters read at least 4.5:1. The button counter is framed in the text colour instead of a tinted fill.
- Toast types are read regardless of case; `download` can also be a file name in a JavaScript event.
- Preset colours: links, the active menu item and focus frames use the button's own colour (each preset's `--color-brand-600` is its button fill). The `dark` preset is a neutral grey in the dark theme.
- Custom colours: the button text stays the same on hover (the background gets 12% black, or 12% white where dark text would not read). The dark-theme tone stands out 3:1 on every dark surface, the lightest being zinc-800.
- `--ui-focus-ring` sets the colour of the focus ring, with the `outline-focus` and `ring-focus` utilities.
- A modal or drawer whose parts a nested Livewire component draws keeps its accessible name after Livewire updates.
- Tab stays inside an open modal `<dialog>` within a trapped panel (the form modal's delete dialog).

### Breaking changes

- `<acun:*>` tags render from the kit's own `acun` namespace: copies in `resources/views/vendor/acun-ui/components/ui/` are now used, and `resources/views/components/ui/` no longer overrides `<acun:*>`.
- `acun:input`, `select`, `textarea`, `checkbox`, `radio` and `input-group` put `class`, `style`, `x-show`, `x-cloak` and `wire:key` on the outer wrapper; use `input-class` to style the control. `acun:search` moves `style`, `x-show` and `wire:key` there too.
- `acun:checkbox` keeps its `<label>` as the root when an error shows; the message is a `<span>` inside it.
- Unsafe links (`javascript:`, `data:`, another host's `//host`) print `#` in every link prop, and a warning is logged.
- `acun:search` with an unsafe `action` searches with GET on the current page, without a CSRF token.
- The locale layer left the kit: `SetLocale`, `Localization`, the `acun-ui.locale` route and config. `acun:locale-switcher` only draws and needs `action` and `locales`.
- `WithToasts::toast()` and `toastAfterRedirect()` have a new `bool $download = false` parameter.
- Field ids repeated in one render get `-2`, `-3`.
- `lang/tr.json` lost the keys `Showing`, `of`, `to`, `results`, `Static`, `open`, `close` and `move`: the pagination summary is one sentence (`Showing :first to :last of :total results`).
- `navbar-mode="hidden"` hides the top bar only from `lg` up.
- The layouts wrap the page content in `<main id="main-content">`.
- Tailwind CSS 4.1 or newer is required: `panel.css` uses `@source inline()`.
- The select fix (writing a `<select wire:model>`'s value again after a Livewire update) is opt-in: `config('acun-ui.select_sync')` or `data-acun-select-sync` on a container.
